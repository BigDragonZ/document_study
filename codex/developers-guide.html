把 Codex 接进真实的软件开发工作

Developers（开发者）栏目说明如何用 Codex 处理代码、选择运行环境、扩展重复工作流、连接团队工具，并把 Codex 集成到自动化系统中。

先理解目录：这是开发者文档的导航总览，涵盖从日常编码到构建集成的不同深度。初学者可先从代码审查、集成终端和本地环境开始；SDK、App Server、GitHub Action 属于集成开发主题。

02

日常开发：工具协作与代码审查

Development workflows

集成终端让 Codex 在开发环境中运行命令；Code review 用于审查变更、查找风险并提供可检查的意见。审查结果是线索，仍需开发者阅读 diff、判断上下文并运行适当验证。

Integrated terminal（集成终端）

让 Codex 在当前开发环境中使用终端完成命令行工作。它与网页聊天中的纯文本对话不同，执行效果受运行环境、配置和权限边界影响。

Code review（代码审查）

围绕已有改动进行检查，帮助发现缺陷或潜在问题。它补充人工审查，不等于测试，也不能证明代码没有问题。

建议顺序：给出任务和项目背景 → 实施修改 → 查看差异 → 运行与改动相匹配的验证 → 对审查发现逐项判断和修正。
03

先选工作在哪里运行

Local · Worktree · Cloud
环境发生在哪里适合情境重点边界
Local（本地）当前电脑上的项目目录需要本机文件、工具和快速迭代。遵循当前本地工作区及权限设置。
Worktree（工作树）本机独立 Git 工作树隔离一项开发任务，避免直接改动当前 checkout。仍在本机运行；文件改动位于单独工作树。
Cloud（云端）Codex 远程工作区远程执行较长任务，或复用准备好的环境。需准备仓库、依赖和工具；云端环境与本地权限并非同一边界。

环境选择和权限选择是两个相关但不同的判断：前者回答“任务在哪里运行”，后者回答“任务在那里能访问什么、哪些操作要审查”。Cloud 环境也需要配置和验证，不会自动继承你电脑上的全部资源。

04

扩展与自动化：别把概念混在一起

Skills · Hooks · WebMCP

Skill（技能）

封装可重复使用的工作步骤、指引和材料，帮助 Codex 按同类方法完成任务。重点是“如何做”。

Hook（钩子）

在预先定义的生命周期事件触发命令或动作，适合确定性的自动化检查。重点是“何时自动触发”。

WebMCP / Site tools

为网站提供可调用的工具接口，让兼容的 agent 能以结构化方式完成网站操作。重点是“网站能提供什么操作”。

Annotations Extensibility

扩展 Codex 对代码位置或变更的注释能力，适合把额外上下文带进审查或开发体验；细节依赖该文档说明。

选择方法：固定重复流程用 Skill；需要事件后自动执行固定操作时看 Hooks；想让网站暴露结构化操作时看 WebMCP。可组合使用，但功能定位不同。

05

把 Codex 接入产品和团队工具

Build with Codex

Codex SDK / App Server

面向开发者：把 Codex 能力集成到自己的应用或系统，或以协议接口管理会话和交互。需要工程实现和运行维护。

GitHub Action / Non-interactive mode

将 Codex 放入自动化流程，例如从命令行非交互执行，或在 GitHub 工作流中运行。适合可重复的 CI 或后台任务。

GitHub、GitLab、Slack、Linear

从团队常用的代码托管或协作系统发起、委派或跟踪 Codex 工作。具体触发方式和可用性由连接与工作区设置决定。

CLI customization / Developer settings

分别查阅命令行与 IDE 扩展的设置。不是每项 IDE 扩展设置都属于 Codex 的 config.toml。

从浅到深：单人本地工作 → 隔离任务 → 可复用云环境 → 团队工具连接 → SDK 或 API 集成。先确认需求，再采用相应复杂度的入口。
