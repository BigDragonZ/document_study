练习 02 · 把想法说成好任务

让 Codex 知道要做什么，
也知道做到什么程度。

一条好任务不必很长，但要补齐会影响行动和判断的信息。把目标、背景、限制和验收说清楚，Codex 才更容易一次走对方向。

01 / 目标

要得到什么结果？

用可以观察的结果描述想做的事，避免只说“帮我处理一下”。

02 / 背景

现在是什么情况？

补充项目状态、已有配置和缺少的东西，让 Codex 不必猜。

03 / 限制

哪些边界要遵守？

说明不能丢失什么、先做什么、哪些改动需要克制。

04 / 验收

怎样算完成？

写出可核对的结果，例如链接、分支、提交记录或运行表现。

真实练习

把“初始化 Git 并发布”说具体

最初的想法已经说出方向；再补上检查步骤、保护边界和验收结果，任务就更安全，也更容易核对。

起初

目标：初始化 Git 仓库并提交。背景：Git 已配置，GitHub 还没有创建对应仓库。验收：提交并发布当前仓库内容到 GitHub。

补充后

先检查当前目录的 Git 状态，确认是否已经初始化仓库，并查看现有文件和未提交的改动。如果尚未初始化，请初始化并提交当前项目内容；不要覆盖或丢弃已有内容。然后在 GitHub 创建对应的私有仓库并推送当前分支。完成后告诉我仓库地址、分支和提交记录。

为什么这样更清楚

  • 先检查状态，避免把已有仓库当成空目录。
  • 明确保留现有内容，给出了安全边界。
  • 把“发布成功”拆成仓库、分支和提交记录，方便核实。
  • 说明私有可见性，避免对仓库公开程度产生歧义。
中途也可以校准

如果 Codex 的理解和你的目标不一致，直接补充缺少的背景或调整验收标准，不必等它做完才纠正。

轮到你

选一个你最近想完成的小目标，分别写下目标、背景、限制和验收。发送前再问自己：Codex 是否知道该先检查什么？有没有需要保护的内容？完成后我能看到什么证据？

练习 03 · 让项目说明替你记住规则

把会反复交代的事，
写进项目自己的说明里。

任务提示适合说明“这一次要做什么”；`AGENTS.md` 适合保存这个项目长期有效的背景和约定。Codex 会把它作为项目指导来参考，但文件内容仍要由你核对。

01 / 项目目标

这个项目是做什么的？

用一两句话讲清服务对象和希望达成的结果。

02 / 技术与运行

如何开始和预览？

记录真实使用的技术、入口文件和必要命令。

03 / 长期约定

哪些习惯要保持？

写下代码风格、页面设计或验证方式等稳定规则。

04 / 操作边界

哪些事情需要谨慎？

记录项目特有的限制，以及需要先检查或询问的操作。

用当前项目做例子

一份短小、可执行的项目说明

这些内容来自你刚刚确认的项目目标和当前文件，不需要搬进所有背景资料。

# AGENTS.md

## 项目目标
这是一个 Codex 自学网站，引导用户循序渐进地学习 Codex，并成长为熟练的 Codex 使用者。

## 技术与预览
- 使用原生 HTML、CSS 和 JavaScript。
- 本地从 index.html 预览。
- 无需安装依赖或运行构建工具。

## 页面约定
- 沿用现有视觉风格。
- 维护移动端布局。
- 修改页面内导航时，确认链接目标存在。

写规则时记住

  • 写长期有效的项目规则；单次任务目标仍放在当前对话。
  • 先从 README 和现有代码核对事实，不把猜测写成要求。
  • 规则要具体到 Codex 能照着做，也不要把说明写得冗长。
  • 改规则文件前先看已有内容，避免覆盖团队已经确认的约定。
先起草，再确认

可以让 Codex 先阅读项目并提出草案，指出每条规则依据；你核对准确后，再决定是否写入根目录的 `AGENTS.md`。

轮到你

挑出三条你希望 Codex 每次进入项目都遵守的规则。分别判断：它是项目事实、长期约定，还是只适用于某一次任务？只把前两类中确实稳定的内容写进项目说明。

练习 04 · 审查、验证，再发布

先看清改了什么，
再带着证据交付。

Codex 完成任务后，工作还没结束。先检查改动是否符合目标，再用合适的方法验证，最后提交并推送；如果要上线，还要确认部署结果。

01 / 审查

检查全部改动

看 Git 状态、差异和新文件，确认内容都在任务范围内。

02 / 验证

收集实际证据

按项目特点运行检查，并亲自查看关键页面或功能。

03 / 提交

保存一个清楚的版本

只暂存确认过的文件，再检查暂存差异并写明提交目的。

04 / 发布

推送并确认结果

推送到目标分支；若触发部署，再查看工作流是否成功。

用这个静态网站做例子

每一步都要有对应证据

不同项目要用不同的验证方法。不要因为运行了一个命令，就默认页面体验、发布流程也都没问题。

审查与验证

git status 检查修改和未跟踪文件；阅读差异，确认范围。对于这个网站，还要检查页面内链接、移动端布局和复制任务按钮，并运行 git diff --check。

提交与发布

确认暂存内容后创建本地提交，再将 main 推送到 GitHub。推送只说明源码已上传；本项目的 GitHub Pages 工作流还要运行成功，才能确认网站部署完成。

交付前核对

  • 所有改动都已看过，包括新文件和暂存区内容。
  • 验证方式与本次改动相匹配，结果有实际输出或页面证据。
  • 提交中只包含这次确认要交付的文件。
  • 推送后检查 GitHub Actions；部署任务成功后再分享网站地址。
Codex 审查是额外一双眼睛

它可以帮忙找问题，但不能代替适当的检查、人工判断和发布结果确认。

轮到你

下次完成一项改动时，先让 Codex 只读审查 Git 状态和差异，再决定是否修正；随后明确验证方式。提交前查看暂存内容，推送后确认工作流结果，并记录提交号和部署地址。
