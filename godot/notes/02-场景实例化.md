# 02：场景实例化

## 学习目标

读完后，你应能把场景当作可复用模板，区分源场景默认值、实例覆盖值和共享 Resource。

## 1. PackedScene 与实例

保存为 `.tscn` 的场景会把节点结构打包起来，因此称为 **PackedScene**。把它放进另一个场景，就创建了一个**实例（instance）**。

可以把源场景理解为蓝图：

```text
ball.tscn（源场景）
├── Ball A（实例）
├── Ball B（实例）
└── Ball C（实例）
```

每个实例都从相同结构开始，但拥有独立的运行时状态。例如多个球可以处于不同位置，分别下落和弹跳。

这里的场景实例化与渲染优化中的硬件实例化不是一回事。

## 2. 三种修改及其结果

### 修改源场景

打开 `ball.tscn`，修改根节点的默认属性并保存。所有没有覆盖该属性的实例都会采用新默认值。

### 修改一个实例

在 `Main` 中选中某个 Ball 实例并修改属性，只会覆盖这个实例。Inspector 会在被覆盖的属性旁显示恢复按钮。

### 恢复实例覆盖值

点击属性旁的恢复按钮，会移除该实例的覆盖值，让它重新跟随源场景。

可以用下面的规则判断：

> 源场景提供默认值，实例覆盖值优先；源场景之后的修改不会冲掉实例已经覆盖的属性。

## 3. 位置与运行时状态

在编辑器中拖动不同实例，本来就会给它们不同的 `position`。运行后，每个实例还会继续独立更新自己的位置、速度、成员变量等。

“结构来自同一模板”不意味着“运行时数据共享”。这是实例化适合复用玩家、敌人、子弹和道具的原因。

## 4. Resource 为什么可能一起变化

节点实例彼此独立，不代表它们引用的所有 Resource 都自动独立。

例如多个实例可能引用同一个 `PhysicsMaterial` 资源。如果在实例上直接编辑这个共享资源，其他引用者也可能看到变化。

如果只想修改当前实例使用的资源：

1. 在 Inspector 中找到对应 Resource 属性。
2. 右键该属性。
3. 选择 **Make Unique**。
4. 再编辑这个独立副本。

先判断你要改的是“节点属性”“源场景默认值”还是“共享 Resource”，再动手。

## 5. 用场景思考项目结构

Godot 官方建议从玩家能看到的游戏对象出发组织场景，而不是先套用复杂架构。例如一个小型躲避游戏可以拆成：

```text
Main（组织流程）
├── Player（玩家场景实例）
├── MobSpawnPath（敌人生成路径）
├── Timers（开始、生成、计分）
└── HUD（界面场景实例）

Mob（敌人场景，由 Main 在运行时创建）
```

这样划分有三个好处：

- **复用**：同一场景可以创建多个实例。
- **封装**：玩家内部如何显示和碰撞，不必全部暴露给 Main。
- **协作**：设计、美术和程序可以分别处理较清晰的场景边界。

## 常见误区

- **修改源场景后，某个实例没有变化。** 检查该实例是否覆盖了这个属性。
- **只想改一个实例，其他实例却跟着变。** 检查是否正在编辑共享 Resource；必要时 Make Unique。
- **把场景实例化理解成复制粘贴。** 实例仍与源场景保持默认值和覆盖关系。
- **一开始设计庞大架构。** 先用少量职责明确的场景完成可运行版本。

## 小结

场景是可复用模板，实例拥有独立状态；实例属性可以覆盖模板默认值，而 Resource 默认可能被共享。掌握这三层关系，能避免大量“为什么它也跟着变了”的问题。
