CONFIGURATION · 08

把便利放在前面，
把边界写在下面。

设置决定 Claude 怎样工作，权限决定它能做什么，沙箱限制命令可触及的资源。三者配合，而不是相互替代。

01 · Settings files

先确定这项设置应该影响谁。

作用域文件用途
User~/.claude/settings.json你在本机所有项目的个人偏好
Shared project.claude/settings.json提交给团队的权限、Hooks、Plugins 等
Project local.claude/settings.local.json你在单个项目的个人覆盖，不应共享
Managedmanaged-settings.json 等组织部署的安全与合规策略

安装 Claude Code 不会自动创建所有设置文件。可手动创建，或由 /config、持续权限批准等功能写入。云端会话在另一台机器运行，不会读取本机 user/local 文件；共享项目设置能否生效取决于云环境与会话类型。

本地文件

Claude 写入 settings.local.json 时会处理 Git 排除；如果你手动创建，应自行加入 .gitignore。不要把个人覆盖和 secrets 提交进团队配置。

02 · Precedence

同名设置通常高优先级覆盖，列表通常合并。

一般优先级从高到低为：Managed settings → Command line（--settings）→ Project local → Shared project → User。命令行覆盖只影响本次会话，不会改写文件。

本次会话临时试用一个设置
claude --settings '{"spinnerTipsEnabled": false}'

环境变量不属于这五个固定层级：每个变量与设置键的组合有自己的优先规则。permissions.allow 等列表通常会合并，而不是整个替换；部分模型列表和安全敏感键有特殊规则。

“高优先级覆盖”不是适用于所有键的简化定律。团队文件并非每个键都能设置，某些安全限制会采用更严格值。采用关键配置前查 All settings 中的作用域与例外。

03 · Change + confirm

修改之后，确认它真的被加载。

设置文件是严格 JSON：不能有注释或尾随逗号。可用 /config 修改常见个人选项，也可编辑文件；/status 的 Setting sources 用于查看当前加载来源，claude doctor 可诊断无效条目。

~/.claude/settings.json · 教学示例
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
  1. 1
    先选正确作用域

    个人偏好不必写进团队文件；组织强制要求不能靠本地覆盖。

  2. 2
    保持 JSON 有效

    保存后检查错误与警告。部分条目无效时可能只跳过那些条目，而不是整个文件。

  3. 3
    确认实际来源

    运行 /status 查看文件是否加载，再针对具体键查优先级和作用域。

  4. 4
    理解生效时机

    许多文件变化会自动重载，但模型等设置有专用切换方式，部分组织键需要重启。

04 · Permission modes

减少打扰，不等于放弃审查。

模式无需逐项询问的基线适用理解
default只读操作入门和敏感工作，编辑与命令按规则询问
acceptEdits读取、工作区文件编辑和常见文件命令愿意事后用 diff 审查编辑，其他命令仍需审批
plan只读探索先研究并提出计划，不修改源代码
auto经后台分类器安全检查的操作长任务减少提示；研究预览，不是安全保证
dontAsk仅预批准工具和只读命令锁定 CI/脚本，其他需要询问的动作直接拒绝
bypassPermissions除受保护路径外跳过权限检查仅限隔离容器或 VM；无提示注入与误操作保护

CLI 中用 Shift+Tab 循环常见模式，或用 claude --permission-mode plan 指定启动模式。Auto 有账号、模型、提供商和组织要求，并非所有用户都可用。

不要在日常主目录或含真实凭据的环境中把 bypassPermissions 当作“提速选项”。官方建议仅在无互联网的隔离容器、VM 或 devcontainer 中使用。

05 · Rules + protected paths

模式设定基线，规则处理具体工具。

allow 预批准明确操作，ask 要求确认，deny 阻止匹配动作。规则可针对 Bash 前缀、文件路径或 MCP 工具，范围越精确越容易审查。

优先精确规则

允许 npm run lint 不等于允许 npm run 任意脚本；通配符匹配要从官方语法核对。

Deny 用于硬边界

真正不能发生的操作不要只写在提示或 CLAUDE.md 中，auto 模式中的对话边界也可能因压缩丢失。

受保护路径

.git、IDE 配置和 Claude 自身关键配置有额外写入保护；不同模式下分别询问、分类或拒绝。

使用 /permissions 查看和调整规则，定期检查“永久允许”是否仍符合当前项目风险。

06 · Sandboxing

权限决定“是否允许”，沙箱限制“实际能到哪里”。

内置 sandboxed Bash tool 在操作系统层限制命令的文件系统和网络访问。可以用 /sandbox 配置边界，让常规命令在范围内更自由地运行，同时减少外部影响。

文件系统边界

限定命令能读写的目录，减少工作区外修改和敏感文件暴露。

网络边界

限制命令可连接的主机，降低数据外发和不可信下载风险。

并非所有操作的沙箱

它主要约束 Bash；MCP、其他工具和外部服务仍需各自权限与信任判断。

更强隔离

高风险或不可信工作可考虑 devcontainer、Docker 或 VM，按威胁模型选择。

07 · Model + terminal

最后才是个性化体验。

/model 调整模型，/effort 调整推理投入。模型切换会影响速度与成本，也会触发新的 prompt cache 读取；不必为了简单任务盲目选择最高配置。

/config 与 /theme

调整常见个人设置与颜色主题；不替代直接编辑完整 settings JSON。

/terminal-setup

配置部分终端的 Shift+Enter 等快捷键；具体支持因终端和平台而异。

/statusline

自定义状态栏，持续查看上下文、成本或 Git 状态等你真正需要的信息。

08 · 实战练习

为练习项目写一份最小配置。

  1. 运行 /status 和 /permissions，记录当前加载来源与权限模式。
  2. 在练习项目创建共享 .claude/settings.json，只加入一条精确 lint/test allow 和一条敏感文件 deny。
  3. 保存严格 JSON，重开或观察重载后用 /status 核对来源。
  4. 分别尝试 default 与 plan 的只读任务，比较哪些动作会触发审批。
  5. 删除不再需要的 allow，记录个人、团队和组织配置应分别放在哪里。
完成标准配置有效、来源可见、权限规则尽量窄；你能解释权限模式与沙箱的区别，以及为什么不在日常环境使用 bypass。
