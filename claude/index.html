练习 02 · 把想法变成好任务

既说清想去哪里，
也说清怎样算到达。

Claude 能自己探索实现路径，不必替它安排每一步。你更需要提供会改变结果的目标、上下文、限制和验收方式。

01 / 目标

要改变什么行为？

描述用户能观察到的结果，而不只是“优化一下”或“修个 bug”。

02 / 上下文

该看哪些证据？

给出错误日志、复现步骤、相关文件或截图；也可以用 @ 引用文件。

03 / 边界

什么不能改变？

说明兼容要求、保护范围，以及部署、推送等需要另行确认的操作。

04 / 验证

什么证据算完成？

提供可运行的测试、构建、截图对照或具体输出，让结果能被检查。

真实练习

把“修复登录问题”说具体

模糊的描述也能开始对话，但完整的证据与完成条件能减少来回纠正。

起初

登录有 bug，帮我修一下。

补充后

用户在会话过期后登录会停留在空白页。请先复现并检查 src/auth/ 中的令牌刷新流程，保持现有 API 不变。先写一个能复现问题的失败测试，再做最小修复；运行相关测试并报告命令、结果和修改文件。不要提交或推送。

为什么更有效

  • 症状和位置缩小了调查范围，但不替 Claude 预设根因。
  • 先写失败测试，让修复有前后对照。
  • API 不变与不要推送是清晰的行为边界。
  • 命令、结果和文件清单让交付可以复核。
复杂任务先计划

多文件改造或方向尚不明确时，用 Plan Mode 先探索、评审方案，再进入实现。小而明确的修正不必增加这道流程。

轮到你

选择一个最近想完成的小任务，写下目标、上下文、边界和验证。发给 Claude 后观察：它是否能自己找到证据并完成检查？如果不能，缺少的是哪一项？

练习 03 · 让项目记住长期约定

把反复交代的事，
写进 CLAUDE.md。

CLAUDE.md 在每个会话开始时提供持久项目上下文；auto memory 则记录 Claude 从协作中学到的偏好和模式。两者用途不同，也都不是强制权限。

01 / 项目事实

怎样运行与验证？

记录无法仅从代码猜出的启动、构建和测试命令。

02 / 项目约定

哪些风格要保持？

写下区别于默认习惯的架构决定、代码风格和目录边界。

03 / 工作方式

交付前做什么？

保存稳定、可执行的检查要求，而不是一次任务的全部步骤。

04 / 强制边界

什么不能只靠提示？

绝不能例外的规则用权限或 Hooks 落实，别只写一句“千万不要”。

用本手册项目做例子

短而具体的项目说明

可以用 /init 生成草稿，再由你核对和删减。只保留每次会话都真正有用的内容。

# CLAUDE.md

## 项目目标
Claude Code 中文实战学习网站，按专题组织官方文档笔记与练习。

## 技术与预览
- 原生 HTML、CSS、JavaScript，无需安装依赖。
- 直接打开 index.html；本地 HTTP 预览用 python3 -m http.server 8000。

## 页面约定
- 沿用现有视觉和课程页结构。
- 每页保留官方来源与核对日期。
- 检查移动端布局、站内链接和复制按钮。

写规则时记住

  • 能从代码直接看出的内容不必重复罗列。
  • 偶尔使用的长流程更适合 Skill，而不是塞满每次上下文。
  • 项目共享规则放进 CLAUDE.md；个人偏好放合适的作用域。
  • 运行 /context 查看上下文，用实际行为验证规则是否有效。
记忆需要维护

规则失效时先检查它是否过长、含糊或没有加载，而不是继续堆叠更多强调词。

轮到你

挑出三条你希望 Claude 每次进入项目都知道的事实或约定。删除它本来就能可靠推断的内容，再用一次真实任务验证效果。

练习 04 · 用证据完成闭环

不是“看起来完成”，
而是验证后交付。

官方最佳实践强调：给 Claude 一个能运行的检查，它就能读取结果并继续迭代。最终仍要由你审查改动与证据。

01 / 审查

看全部改动

检查 Git 状态和 diff，确认文件与变化都在任务范围内。

02 / 验证

运行真实检查

测试、构建、lint 或浏览器截图必须与这次任务相匹配。

03 / 复核

找遗漏而非凑数量

代码审查关注正确性、边界和要求，不盲目追逐每条风格建议。

04 / 交付

报告证据与限制

列出命令、结果、未验证事项；提交、推送和部署另行授权。

闭环工作方式

让检查成为任务的一部分

在请求中直接给出测试用例、复现步骤或目标截图，比完成后再补问“你确定吗”更可靠。

实现与自查

实现 validateEmail。用有效、无效和边界输入写测试；实现后运行测试并修复失败，不改变现有函数签名。

审查与交付

检查最终 diff 是否只包含目标改动，报告实际运行的命令和结果。若某项无法验证，请明确写出，而不是用“应该可以”代替证据。

安全网各有边界

  • Checkpoint 可以回退 Claude 做出的文件修改，但不能撤销外部系统副作用。
  • Checkpoint 不是 Git 的替代品，外部进程产生的改动也不一定被跟踪。
  • 测试通过不代表所有体验都已验证，UI 仍要看真实页面。
  • 云端部署、数据库与远端 Git 操作需要单独检查其影响和授权。
先保存自己的工作

在让 agent 进行大范围改动之前，确保你理解当前版本状态，并知道怎样恢复。

轮到你

选一个已完成的小改动，让 Claude 只读审查 diff 并列出验证缺口。你亲自运行关键检查，再比较它的判断与实际证据。

学习的方法

每学一点，
就用它做点什么。

A

从真实任务开始

用手边的小项目练习，不从背术语开始。先读官方概念，再用自己的任务验证。

B

让结果可检查

每节课都有操作和完成证据。命令、测试、截图与 diff 比“应该完成了”更可靠。

C

理解边界再扩展

先掌握核心协作，再增加插件、自动化与团队配置；功能越多，越要理解权限与上下文成本。
