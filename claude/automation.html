01 · Run agents in parallel

先决定谁协调、是否通信、是否修改同一批文件。

方式协调方式适合场景
Subagents主会话委派并接收摘要调查、专项审查、避免主上下文膨胀
Agent view你分派并监控多个后台会话多个独立任务，需要时介入；研究预览
Agent teamsLead 分配，成员共享任务并通信需要自动拆解与协作；实验性且默认关闭
Worktrees你或 agent 在独立 Git checkout 工作并行编辑，避免文件冲突
/batch拆分大改动到多个 worktree subagents可用一条指令描述的仓库级机械迁移

claude agents 打开后台会话的 agent view；/agents 管理当前会话的 subagents；/tasks 查看后台任务。名字相近，但管理对象不同。

组合而非二选一

Subagent 解决上下文与职责分工，worktree 解决文件隔离，可以一起使用。并行会增加 token 用量和审查工作，不是数量越多越好。

02 · Worktree isolation

每个并行编辑会话，都有自己的工作目录。

Git worktree 与主 checkout 共享仓库历史和远端，但拥有独立文件与分支。--worktree 默认在 .claude/worktrees/<name>/ 创建目录和 worktree-<name> 分支。

两个隔离会话 · 分别在终端启动
claude --worktree feature-auth
claude --worktree bugfix-123
  1. 1
    初始化新环境

    worktree 是新 checkout，依赖和本地设置可能需要重新安装或配置。把 .claude/worktrees/ 加入 .gitignore。

  2. 2
    明确基点

    默认从仓库默认分支创建；需要基于当前 HEAD 时，核对 worktree.baseRef 设置。

  3. 3
    退出前检查工作

    干净会话和含改动会话的清理行为不同。删除会丢弃其中的未提交工作甚至新提交，必须读清提示。

  4. 4
    理解隔离边界

    它主要隔离文件编辑，并非完整安全沙箱；共享 Git 元数据、权限批准和部分配置，命令写入仍需权限控制。

非交互 -p 运行没有退出清理提示，不会按交互流程自动清理 worktree。使用 git worktree list 检查状态，确认无未保存工作后再按官方步骤处理。

03 · Programmatic CLI

用 -p 把 Claude 变成可组合的 Unix 工具。

非交互模式以前称 headless mode。claude -p "prompt" 执行任务后退出，适合脚本、CI 和批处理。输出可以是 text、json 或 stream-json。

只读摘要与 JSON 输出
claude -p "Summarize this project and list its test commands"
claude -p "Summarize this project" --output-format json
claude -p "Explain this build log" --output-format stream-json --verbose < build.log
text

默认纯文本，适合直接阅读或简单管道。

json

包含 result、session ID 与元数据；可配合 JSON Schema 获得结构化结果。

stream-json

逐行 JSON 事件，适合实时处理；多行拼接整体不是一个普通 JSON 数组。

--allowedTools 会扩大非交互任务可自动使用的工具。先从只读或精确规则开始，例如 --allowedTools "Read,Glob,Grep"，不要用宽泛 Bash 权限换取方便。

用户显式调用的 Skills 和交互命令并不一定适用于 -p。自动化中用普通语言描述目标，并在小样本上验证输出格式与退出行为。

04 · Scheduled + background work

重复发生的事，才值得定时。

会话内 /loop

在当前 CLI 会话中按间隔重复提示，适合临时轮询和短期观察；会话生命周期会影响它。

Desktop scheduled tasks

在本机运行，能访问本地文件和工具，适合每日审查或本地晨报。

Cloud scheduled tasks

在云端按计划、API 或 GitHub 事件触发，电脑关机也能继续；原称 routines。

定时前先把同一提示手动跑通，并定义输出、异常处理和停止条件。云端任务还要考虑仓库、环境、通知、使用量与组织策略。

05 · CI/CD + code review

把 agent 接入流水线，也把权限和结果纳入审查。

GitHub Actions 与 GitLab CI/CD 可以响应提及、自动处理 issue、执行维护和生成修改。托管 Code Review 则可对 GitHub PR 自动验证发现并留下行内评论。

触发条件

明确谁、什么事件和哪些分支能启动任务，避免不可信输入直接获得高权限工具。

凭据与写入

令牌遵循最小权限；区分只读审查与提交、推送、评论、部署等外部副作用。

结果验收

把测试和人工审查留在流水线中，记录 agent 输出、成本和失败状态。

本地 /code-review 与组织级托管 Code Review 不同：前者在当前工作流中按需运行，后者由组织为仓库开启并自动审查 PR。

06 · Scale safely

自动化程度越高，完成条件越要确定。

  1. 先在 2–3 个小样本上跑通，再扩大文件数、并发数或触发频率。
  2. 限制工具、目录、网络、分支和外部服务，不用宽泛权限代替任务设计。
  3. 提供可运行检查和结构化输出，失败时让流水线真正失败，而非只打印建议。
  4. 让独立审查者核对 diff 与要求，避免实现者自己给自己打分。
  5. 记录 token、频率和人工审查成本；并行与定时都可能放大消耗。
  6. 为 worktree、云环境、远端分支和生成物设计清理与恢复方式。

07 · 实战练习

先自动化一个只读任务。

  1. 选一个无写入的重复任务，例如总结当前项目测试命令或分析一份公开构建日志。
  2. 在交互会话中把提示和验收格式跑通，再改写为 claude -p。
  3. 分别获得 text 与 json 输出，检查字段、错误处理和内容是否符合要求。
  4. 如果需要并行编辑，先在临时 Git 练习仓库尝试一个 worktree，而不是直接用于重要分支。
  5. 记录试跑结果、权限和清理步骤，再决定是否值得进入定时或 CI。
完成标准只读自动化能重复产生可解析结果，没有宽泛工具授权；你能说明扩展到并行或 CI 前的验证、权限与清理方案。
