DAILY WORKFLOWS · 04

把任务交给它，
把判断留给自己。

好的工作流不是固定咒语，而是让目标、证据和验证在正确的时间出现。从代码探索到 PR，每个环节都能复盘。

01 · Understand a codebase

先广后窄，再沿调用链深入。

进入陌生项目时，先要高层地图，再定位与当前任务有关的模块。Claude 会按需读文件；你可以用项目自己的领域词汇缩小搜索范围。

  1. 1
    建立全局认识

    询问项目用途、主要架构、关键数据模型、启动与测试方式，并要求文件路径证据。

  2. 2
    定位相关实现

    例如“找出处理用户认证的文件，并解释它们怎样协作”。

  3. 3
    追踪真实流程

    要求“从前端表单到数据库跟踪登录流程”，再针对一个节点继续追问。

EXPLORATION PROMPT

先只读探索 src/auth/。总结登录从 UI 到令牌存储的调用链，标出每一步的文件和函数；再列出修改令牌刷新逻辑前必须理解的三个约束。不要改文件。

避免无限探索

给调查明确问题、目录范围和输出形式。需要阅读大量文件时，可用独立上下文的 Subagent，并把结论带回主任务。

02 · Fix bugs

先让问题稳定出现，再让修复证据消失。

把错误文本、复现命令、稳定或偶发情况告诉 Claude。修复不应只消除报错表面，还要针对根因并用回归检查证明。

复现

记录操作步骤、输入、环境、完整错误和预期行为；能运行就先跑出失败。

定位

沿调用链验证假设，区分根因与连带症状，不因某个文件显眼就先改它。

回归

先保留能复现问题的失败测试，再修复并跑相关测试，防止相同问题回来。

DEBUG PROMPT

npm test 中 auth.spec 的“过期令牌刷新”稳定失败，错误如下：[粘贴错误]。请先复现并查明根因，添加能覆盖此场景的回归测试，再做最小修复。保持公开 API 不变，运行相关测试并报告结果。

03 · Refactor + test

重构保持行为，测试验证行为。

重构与功能修改最好分开，小步进行并持续运行检查。编写测试时，Claude 会参考项目现有测试风格；你应明确真正要验证的行为，而不是只追求覆盖数字。

安全重构

指出现代化目标、兼容约束与不可变行为。要求小步修改，运行已有测试并检查公共接口。

有意义的测试

覆盖正常路径、边界、错误输入和回归场景；沿用项目测试框架，避免无目的 mock。

两个独立的小任务
将 utils.js 中的 callbacks 重构为 async/await，保持现有公开行为和 API 不变。分小步修改，每步运行相关测试。

为 NotificationService 补充边界与错误路径测试。先阅读现有测试并沿用同一框架与断言风格，然后实际运行。

04 · Explore → plan → code

方向不清楚时，把研究和实现分开。

Plan Mode 允许 Claude 用只读方式调查并提出实施方案，适合多文件改造、陌生代码库和需要讨论权衡的任务。小 typo 或单行明确修复不必增加计划开销。

  1. 1
    Explore

    在 Plan Mode 阅读相关文件，询问现状、依赖、风险和缺失需求。

  2. 2
    Plan

    要求列出改动文件、数据/控制流、兼容性、验证和回退。你可以继续纠正计划。

  3. 3
    Implement

    批准合适执行方式后再修改，按约定运行测试、构建或页面检查。

  4. 4
    Deliver

    检查最终 diff，审查证据；需要时再提交或创建 PR，不把远端动作默认混入实现。

以 Plan Mode 启动
claude --permission-mode plan

CLI 中也可用 Shift+Tab 循环权限模式，或用 /plan 为单条任务加上计划前缀。不同版本与界面的具体操作以官方权限文档为准。

05 · Rich context

文件、截图和日志，都可以成为证据。

@ 文件或目录

用 @src/utils/auth.js 明确引用文件。目录引用提供列表，不等于读入目录全部内容。

图片与截图

拖入、粘贴或给出图片路径，用于错误截图、设计稿和架构图；补充截图无法表达的行为要求。

管道与 URL

把日志通过管道交给 claude -p，或提供官方资料 URL。外部内容仍应视为不可信输入。

VISUAL TASK

根据这张设计截图实现页面，沿用项目现有组件和样式。截图未显示的移动端导航、键盘焦点和空状态按以下要求处理：[补充要求]。完成后在浏览器对照截图并修正可见差异。

06 · Review + pull request

审查是独立一环，不是最后一句“没问题”。

/code-review 会审查当前分支改动并返回发现；/review 是其别名。默认不加 --fix 时以报告为主。它可作为额外视角，但不能代替测试、人工判断和实际页面检查。

本地代码审查示例
/code-review
/code-review src/auth
/code-review HEAD~3..HEAD

需要 PR 时，可以先让 Claude 总结改动、风险与验证，再由你审查描述和 diff。使用 /commit-push-pr 会连续提交、推送并创建 PR，属于明确的外部操作，不应在未确认分支、远端与内容时随手运行。

本地 /code-review 与组织在 GitHub 上开启的托管 Code Review 是不同工作方式。后台 --fix 对检查点的覆盖也有特别限制，详见官方本地审查文档。

07 · 综合实战

完成一次有证据的小修复。

  1. 选一个可稳定复现且影响范围小的问题，写下复现步骤和预期行为。
  2. 让 Claude 先只读定位，给出根因证据和最小修改范围；复杂时进入 Plan Mode。
  3. 先产生回归测试或其他可重复失败信号，再实施修复。
  4. 运行相关测试和项目标准检查；UI 变化还需在真实浏览器查看。
  5. 运行 /code-review 或请求独立审查，只处理影响正确性和需求的真实缺口。
  6. 检查 Git diff，记录结果与未验证事项；本次练习先不提交或推送。
完成标准问题能复现，修复有回归证据，最终 diff 在范围内，验证命令真实通过；任何未检查项都被明确写出。
