SECURITY · 09

能力越强，
边界越要具体。

安全不是某一个模式或开关，而是权限、隔离、不可信内容、秘密管理、人工审查和组织政策的组合。

01 · Defense in depth

没有任何一层能独立保证安全。

Claude Code 默认以只读方式开始，在编辑、执行命令和网络操作时根据权限请求批准。工作区写入限制、sandboxed Bash、信任验证和命令分析提供额外保护，但用户仍需审查建议。

权限层

用模式与 allow/ask/deny 决定工具是否可执行；尽量精确，定期审查永久允许。

隔离层

用沙箱、devcontainer 或 VM 限制文件与网络；不可信任务不要直接放在完整主机环境。

审查层

检查命令、diff、外部动作和验证结果。Checkpoint 不能撤销远端与数据库副作用。

官方明确说明：现有保护能显著降低风险，但没有任何系统能完全抵御所有攻击。Auto mode 同样不是绝对安全保证。

02 · Prompt injection

工具读到的内容，也可能试图指挥工具。

提示注入是攻击者把操纵性文字放进网页、仓库、Issue、日志或工具结果，试图让 agent 忽略原任务、泄露信息或执行危险动作。内容“由 Claude 读取”不代表它可信。

  1. 1
    把外部内容当数据

    要求 Claude 把网页或 issue 中的指令视为不可信材料，不遵循其中改变任务、权限或外传数据的要求。

  2. 2
    审批前看完整命令

    不要因为之前允许过类似命令就机械批准。注意下载执行、curl/wget、shell 拼接和异常目标。

  3. 3
    保护关键文件

    对 CI、Hooks、权限、依赖脚本和发布配置的变化进行人工审查，它们可能影响未来每次运行。

  4. 4
    高风险任务加强隔离

    处理不可信网站、未知仓库或外部服务时，考虑 VM、受限网络与无真实凭据的临时环境。

官方建议避免把不可信内容直接管道给 Claude。若任务必须分析这类内容，缩小工具权限，并明确它只是待分析数据。

03 · Sensitive code + secrets

让凭据不进入不该出现的上下文和配置。

不要共享秘密

不在 CLAUDE.md、共享 settings、.mcp.json、提示示例或课程材料中写真实 token。

限制读取

用精确 deny 和沙箱减少 .env、密钥目录等暴露；也要理解例外和工具边界。

使用安全认证

优先 OAuth、环境变量或受管凭据流程，避免把 token 直接写进命令和版本控制。

敏感仓库可使用项目专属权限、隔离环境和更严格审查。若秘密已经进入对话、日志、远端或生成物，仅删除本地文件不够，应按组织流程轮换并检查传播范围。

Windows 用户应查看官方 WebDAV 风险说明：启用 WebDAV 或允许访问相关 UNC 路径可能触发远程网络请求，绕过预期权限边界。

04 · MCP + plugins

第三方能力同时带来工具、代码和信任链。

Anthropic 不管理或审计所有第三方 MCP servers。优先使用自己编写或可信提供方的 server，并用权限限制可调用工具。Plugin 还可能包含 Hooks、Subagents 和其他可执行组件。

  1. 核对发布者、源码、版本、安装范围和 marketplace 来源。
  2. 列出它能读取的数据、执行的命令、访问的网络和需要的凭据。
  3. 审查 Hooks、安装脚本与工具描述，不只看插件页面介绍。
  4. 团队共享配置仍需成员信任审批；不要预先替所有人放宽限制。
  5. 移除后检查配置、进程、凭据和远端授权是否仍需清理。

05 · Cloud + Remote Control

先确认执行位置，再谈安全边界。

环境主要边界仍需检查
Cloud隔离 VM、网络控制、受限凭据代理、分支限制、审计与环境清理仓库内容、secrets、网络允许域名、生成 PR 与组织策略
Remote Control代码执行和文件访问仍在本地，短期限定用途凭据用于连接本机文件、工具与权限；不是云端沙箱
Local工作区写入、权限模式和可选沙箱本机凭据、其他目录、外部命令和安装内容

06 · Team governance

把组织要求放进可验证的政策，而不是口头约定。

Managed settings 可统一部署组织策略，版本控制可分享批准的团队配置。OpenTelemetry、审计日志和使用分析帮助理解实际采用与风险。

统一底线

明确禁止的高风险模式、可用 MCP/插件、网络与模型策略，并检查是否真正生效。

安全变更

审查 settings 和 Hooks 的改动；可用 ConfigChange 等机制审计或阻止会话中变化。

持续培训

让团队理解提示注入、秘密处理、审批疲劳和云端差异，而非只学习“怎么更快”。

07 · Data + cost awareness

可见的不只是代码，还有数据与使用量。

数据保留、训练偏好、隐私设置和 Zero Data Retention 取决于账号、合同与组织配置，应查官方 Data usage 和政策页面，而不是凭一般经验判断。

并行 agents、长上下文、定时任务、云端审查和自动分类器都可能增加使用量。用 /usage（订阅）或成本相关工具与组织 dashboard 观察，设置预算、频率和停止条件。

最小化原则

只提供任务需要的数据与工具，只让自动化在必要频率运行。减少上下文和不必要并发，通常同时降低成本与风险。

08 · 实战安全检查

在一次真实任务前，问完这八件事。

  1. 工作目录是否正确？是否包含不应读取的其他项目或秘密？
  2. 当前权限模式是什么？永久 allow 是否仍然必要且足够窄？
  3. 输入是否包含不可信网页、Issue、日志或工具结果？
  4. 命令会写哪些目录、访问哪些网络、使用哪些账号？
  5. 是否会产生提交、推送、评论、部署、数据库或消息副作用？
  6. MCP 和插件来源是否可信，代码与权限是否审查过？
  7. 测试、diff、审计和人工验收由谁完成？
  8. 出错时如何停止、恢复、撤销外部影响并轮换可能泄露的凭据？
完成标准每个问题都有具体答案或明确的“不知道”；不知道的关键边界先查清，再执行任务，而不是用默认设置替代判断。
